About

What the site shows, what the words mean, how the data were built, and where they come from.

What the site shows

The site has three pages: Explore, Session and About. The Explore page shows weekly trends, headline numbers, distribution cards, 29 figures of the paper in four sections (Sessions, Tools, Prefix caching, Human-driven against benchmark) and a list of every session; the Session page opens any one session.

Every figure is drawn over every week and every harness but eval:swe-bench, the SWE-bench benchmark replay: the paper's population; the benchmark replay appears only where a figure's legend names it. The figures are computed once, when the site's data are built: the site's own queries are run over every week and those harnesses, and the page reads their answers, so it draws at once without a database.

Each figure card shows a title and a one-line caption; its Definition control opens on the figure's full definition, the rows it rests on and, where the site draws more simply than the paper, how. The session list has an answer of its own, every harness's sessions with the benchmark replay's marked, and filters it in your browser by month, harness, main model and size; the month and harness filter is kept in the link, so a filtered list can be shared, and it changes no figure. The Session page reads the one week its session belongs to, fetching that week's files whole, and draws it in your browser: a bar per request with a chip per tool call, and in a request's details each call's programs and, under it, the skeleton of its arguments.

Definitions

These are the pipeline's definitions. Most are computed by the pipeline's own functions when the site's data are built, and the pages filter, count, sum and take quantiles of the results; How the data were built names the queries that restate one in SQL.

Sessions and requests

Request
One call to an LLM through the FreeInference gateway: an input of messages in, a response out. Its start is its arrival at the gateway and its end its completion.
Session
A chain of requests from one account, each continuing an earlier one: it replays a tool-call id that request emitted, or that request's answer reappears in its last assistant message. The release keeps agent sessions, which have at least one tool step and at least two user steps (a SWE-bench run needs only the tool step), and every session they spawned whether or not it passes that rule. A session lies within one week; one that continues into the next week is released there as a new session.
Top-level session
A session that no other session spawned: it has no parent session. The top-level sessions are the population every count, figure and table on this site is drawn from; a subagent's requests are counted only where a page says so.
Subagent
A session started by a tool call of category Subagent in another session, matched to the session whose first user message repeats the call's delegation prompt. Its depth is 1 under a top-level session, 2 under a subagent, and so on. A top-level session's subagents are those at every depth; the top-level session and each of its subagents are its agents.
Account
The FreeInference account that sent a session's requests, released only as a hashed id. Accounts are counted as distinct ids.
Harness
The agent program that sent a session's requests, such as claude-code or codex, recognised from its first request's prompt or user agent. eval:swe-bench is the SWE-bench benchmark replay; the paper's population is every other harness.
Model and provider
The model a request asked for, and the upstream provider that served it, released as an anonymous letter.
Main model
The model of most of a session's own requests, the first in name order on a tie.
Step, user step and tool step
A request's position in its session, counted from 0. A user step is a request whose new input is a user message; a tool step is one whose new input is tool results. A session's first request is always a user step.
Turn
A user step and the tool steps after it, numbered from 1 in each session (the release's own trace lines number them from 0, as turn_index). A turn's duration is its last completion minus its first arrival.
Session duration
A session's last completion minus its first arrival, over its own requests.
Messages and roles
The messages of a request's input; the tool definitions are not a message. The input's tokens by role are counted for the system, user, assistant and tool-result messages and for the tool definitions with the o200k_base tokenizer, not the provider's, so they need not add up to the input tokens.
Finish reason
Why the response ended: stop, length, tool_calls, content_filter or other.

Tokens and caching

Input tokens (prompt tokens)
The tokens of a request's input, as its provider counted them.
Cached and uncached tokens
Cached tokens are the input tokens the provider reported reading from its cache; they are missing where the provider reports no cache reads. Uncached tokens are the input minus the cached tokens, at least 0, and exist only where the provider reports cache reads.
Output tokens
The tokens of a request's response, as its provider counted them.
Hit ratio and cached share
A request's hit ratio, or cached fraction, is its cached over its input tokens, at most 1, where it has an input and its provider reports cache reads; it is missing otherwise. The cached share of a set of requests is their cached tokens over their input tokens, counting only the requests whose provider reports cache reads.
Peak prompt tokens
The largest input of any one of a session's own requests, in tokens.
Transition: append, mutation, switch
How a request's input relates to the previous step's. It is a switch when the two requests' models or providers differ; an append when every message of the earlier input is, unchanged, at the same position of the later one; and a mutation otherwise. A session's first request has none.
Context mutation and its cause
A request whose transition is a mutation: the agent rewrote context it had already sent, and a prefix cache loses what follows the change. Its cause is the first of these that holds where the two inputs first differ: compaction (history replaced by a summary), tool_definitions (the tool list changed), system_prompt, dropped_turns (turns removed and the rest moved up), injection (a message inserted), tool_result, or other.

Time

Wait, and what a request waited for
A request's wait, or gap, is its arrival minus the previous request's completion in the same session; a session's first request has none. A user step waited for the user. A tool step waited for a subagent when the previous request made a Subagent call, for the ask-user tool (a person answering a question) when it made an Ask User call, and for a tool otherwise. The paper names these four causes Tool Gap, Ask-User Tool, User Idle and Subagent; the gap figures draw the requests with a wait of 0 s or more and a cause.
Gap bin
One of six bins of a request's wait, each including its lower bound: <1m, 1–5m, 5–15m, 15–30m, 30m–1h and >1h.
Idle gap
A request's arrival minus the latest completion among the same account's earlier requests at the same provider, in top-level sessions, in any week; a subagent's request has none. The benchmark replay's requests look back over the benchmark replay's only, and every other harness's over the other harnesses' only, as in the paper. It is how long that provider's cache went unused by the account. It is kept for requests with a hit ratio whose account's previous request at that provider also reported cache reads. The idle-gap bins are 26 bins from 10 s to 1 h, each 1.25 times as wide as the one before; gaps under 10 s count as 10 s and gaps over 1 h are dropped.
TTFT
Time to first token: from a request's arrival at the gateway to the first token of its response. A TTFT is trusted when it is positive and under 95% of the request's latency, its end minus its start; figures of TTFT use trusted ones only.

Tools

Tool call
One call to a tool that a request's response emitted; a response may emit several, in order. A tool name used by fewer than three accounts is released as other, with its category kept.
Category
The kind of tool a call used: Read, Edit, Write, Browser, MCP, Ask User or Subagent; for a shell call, the purpose of its command, marked * (*Interpreter, *Search, *File Ops, *Git/VCS, *Network, *Wait/Poll, *Build/Test, *Packages); and Other for a call that no tool family or shell purpose places.
Tool group
One of the eight groups of categories the tool mix along a turn draws: Read, Search, Write/Edit, Execute, Build/Test, Git/VCS, Browser/Web and Other. Read calls are in Read, Edit calls in Write/Edit, Write calls in Write/Edit, *Search calls in Search, *Interpreter calls in Execute, *Build/Test calls in Build/Test, *Git/VCS calls in Git/VCS, Browser calls in Browser/Web and *Network calls in Browser/Web. A *File Ops call is in Write/Edit when the first word of any program it ran changes files (mkdir, rm, mv and the like), else in Read when one only looks (ls, cat and the like), else in Other. A call of any other category is in Other.
Programs
The programs a shell call's command ran, in the command's order, as the release labels them, such as cd, sed; a call that is not a shell call has none.
Argument skeleton
A call's arguments with every value replaced by its type, as the release keeps them: for a shell call its command, such as cd <path> && sed -n <str> <path>; for any other call each argument's name and type, such as path: <path>, diff: <path>.
Outcome
Whether a call succeeded, decided from the strongest evidence at the start of its result: ok, error, denied or timeout; missing when no result carried the call's id. A failed call is one whose outcome is error, denied or timeout.
Tool-call latency
The wait after a call's request until the session's next request; the calls of one response share it. The session timeline therefore starts each call at its request's end.
Result tokens
The tokens of the result that answered a call, counted with o200k_base. The result's text is never released.

Weeks and statistics

Week
Sunday to Saturday in UTC, named by its Sunday. A request belongs to the week in which it completed. The release, the site's data and the cache simulation are each built one week at a time.
Month
A week's month is the month of its Sunday, so a week that spans two months belongs to the first. The session list's month filter keeps the sessions of a month's weeks.
CDF and percentiles
A CDF plots, for each value, the share of rows at or below it. Medians and other percentiles are exact quantiles of the rows, not estimates from bins.

Cache simulation

Cache simulation
A replay of a prefix cache over the 16-token blocks of the inputs of top-level sessions, one week at a time, each week starting with an empty cache: of the paper's population, and on its own of the benchmark replay. Its figures draw one or both, each figure's legend or Definition saying which. A request reads its blocks when it arrives and writes them when it completes; a read is a hit when the gap since the block's previous read completed is at most the TTL and no eviction signal removed the block first, or when the previous request is still in flight and will write the block. A block's first read of the week is a miss.
TTL
The longest gap after which the simulated cache can still serve a block.
Policy
What, besides the TTL, evicts a block. The pipeline simulates four policies; the site keeps and draws one, ttl_only, under which nothing but the TTL does, as the paper's retention figures draw it.
Reusable and dead token-seconds
Tokens times the seconds they are held. A block held in the cache after a request completes is reusable when the block is read again later in the week, whether or not that read hits, and dead when it is never read again. The mean retained tokens are the reusable and dead token-seconds over the span from the week's first request to its last, each summed over the weeks; the normalised prefill is the tokens missed at a TTL over those missed with no TTL.

Where the site draws more simply than the paper

Each figure's Definition says where it differs from the paper; these are all the differences in one place.

  • Every figure: a bin with fewer than 50 rows is hidden, and the figure says how many were; the paper also drops thin size bins, but merges an idle-gap bin of fewer than 20 requests into the next one.
  • Token growth with the context: fixed power-of-two bins of the messages in a request, where the paper fits its bins to the data.
  • Context share by role: each role's share of the input pooled per power-of-two bin of input tokens, tool definitions included, where the paper takes each request's share per bin of messages and its main figure leaves tool definitions out.
  • Token split by week: plain token shares per week, where the paper weights tokens by price and ranks sessions; Cost share by session does that, as the paper does, at the pipeline's prices: cached, uncached and output at 1 : 10 : 50.
  • Time to first token by model and Decode time by model: the five models with most requests that are among the eight with most requests over every week, where the paper draws two fixed models, each with its decode time and an estimate of its queueing time; the site draws no queueing estimate.
  • Tool latency by category and Tool result size by category: percentiles per category, where the paper also marks the mean.
  • Hit ratio after an idle gap: the pipeline's fixed idle-gap bins, each drawn at its middle, a line for each of the eight providers with most requests, where the paper merges a thin bin into the next, draws each bin at its requests' median gap and shows the four providers with most idle gaps.

As in the paper, the hit ratio after a context change leaves out a switch to another model or provider: it is routing, not a change of context.

How the data were built

The site draws the v1 release of the FreeInference agentic trace, published on Hugging Face one week at a time: anonymous JSONL traces, one top-level session per line with each subagent nested under the call that spawned it, and Parquet tables of the sessions, requests and tool calls. The release holds no message text, prompt text, tool results or raw identifiers: accounts and sessions are hashed, providers are letters, and a tool call's arguments keep their structure with every value replaced by its type.

make data reads every week of the release and of the pipeline's cache simulation, both of the paper's population and of the benchmark replay on its own, checks each week against its manifest and tables.json with the pipeline's reader, and writes one Parquet file per kind of row and week, requests/week=<sunday>/rows.parquet and the same under tool_calls/, sessions/ and simulation/ (the last only for the weeks the simulation covers), with weeks.json and harnesses.json. The Parquet files hold some of the release's columns, among them each tool call's programs and argument skeleton, never its block ids, and columns computed by the pipeline's own functions: each row's week and harness, whether its session is top-level, its top-level session and depth; each request's turn, uncached tokens, hit ratio, wait, idle gap and idle-gap bin, whether its TTFT is trusted, how many tool calls it emitted, the tokens of a user step's new prompt, and the tokens it missed with no TTL in the cache simulation; and each session's totals over its own requests. The simulation's files hold its tallies per TTL under the TTL-only policy, for each of the two populations, with each week's span. The idle gap looks back across weeks, so it is computed over every week together, the benchmark replay apart from the other harnesses. weeks.json lists the weeks and says which ones the cache simulation covers; harnesses.json lists the harnesses with their sessions and says which one is the benchmark replay. Last, make data runs every query of the Explore page once in DuckDB, with every week and the paper's population selected (the session list's with every harness), and writes each answer under all_weeks/. The built data ship with the site, so it is served as it is, without building.

In the browser, every figure is drawn from those answers, and the session list filters its answer; the Session page runs its queries with DuckDB-WASM over its week's Parquet files, fetched whole. Neither decides what a turn, a wait or a cache hit is. Every definition comes from the pipeline. Where a query restates one in SQL (the cost share's prices, the rank bins, the wait classes, what a tool wait is and how long it counts for, the tool groups, the simulated TTLs, the cache costs' prices, normalising TTL, knee and lowest-cost rules, the mutation table's rows and which sessions count as appends), a mirror test ties each copied constant to the pipeline's and a parity test ties the number to the paper's; ten queries do, those of Cost share by session, Session time by part, Speed-up if twice as fast, Calls per request by category, Tool latency by batch width, Tool mix along a turn, Context mutations by cause, Prefill against storage, API cost by TTL and Infrastructure cost by TTL. Every number a figure shares with the paper equals the paper's.
