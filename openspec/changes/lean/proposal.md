# Change: lean

## Why
After `simplify` the site is about 8,400 lines of JavaScript and 9,000
of tests for one landing page and one session page. Three things keep
it that size: 31 figures with 29 draw functions for about seven chart
shapes, each restating the frame, ticks, labels and tooltip; a sessions
table that still reads three generations of URL keys no public link
ever used; and tests that pin markup detail by hand while nothing
checks the whole page a visitor sees. Comments are a fifth of the code,
many of them narrative. A maintainer who did not write this should meet
seven chart kinds and a list of entries, one URL format, and one test
that says whether the page changed.

## The aim, and the rule for every task
The aim is a codebase a normal person can maintain, not a smaller one:
ordinary software engineering practice, applied plainly.
Fewer lines are a consequence, never the goal. The rule for every item
and every review: **a change is made only if the code is clearer
afterwards to someone reading it for the first time.** Where removing
or merging something would make a reader work harder, the thing stays,
and the report says so. No tricks: no clever one-liners to save a
function, no module folded into another because one import looked
untidy, no comment cut because it was long. A reviewer rejects a task
that is shorter but less plain.

## What changes
Nothing a visitor sees or can do changes.

- **Snapshot tests first.** The gate script of `simplify` becomes a
  tracked test: for each of nine page states, the normalised text of
  every chart, table, legend and text block, in `tests/snapshots/`,
  compared by `make test` in headless Chromium, regenerated by
  `make snapshots` when a change is meant. Text, not checksums, so that
  `git diff` shows a maintainer what changed in a chart. The unit tests
  that pinned markup go once the snapshots cover them.
- **Figures call shared chart kinds.** Seven plain functions in
  `js/charts/` (CDF lines, stacked bars by week, quantile ranges,
  histogram, ranked areas, lines with a knee, donut), each with named
  parameters. A figure's entry keeps a `draw` that is one visible call
  to its kind with the columns and labels written out, and, where the
  paper's callout needs it, one short function of its own. No string
  dispatch and no option a single figure uses: a figure that would need
  one keeps a plain draw function instead. The runner stops interpreting
  flags.
- **One URL format.** The sessions table reads and writes
  `months`, `harnesses`, `model`, `min`, `search`, `sort` and `page`;
  the `weeks=`, `month=` and `scope=` keys and the old anchors go, with
  their rewriting and tests.
- **Comments say what and why, not the story.** CONTRIBUTING gets the
  rule: a module header says what the module holds and what crosses its
  boundary, an export's docstring states its definition, a comment in a
  function says why; history is not written. A header longer than ten
  lines is a sign to look again, not a failure. The pass applies it to
  the modules the other tasks touch, keeping every sentence a reader
  needs.
- **The specs squashed** into three files and the archive removed, as
  `simplify` decided.

## Before and after
| | After `simplify` | After `lean` |
|---|---|---|
| Figure modules (`figures/`, `simulation/`, `comparison/`) | about 2,500 lines, 29 draw functions | about 1,400 lines, 7 kinds |
| Sessions table stack | about 900 lines | about 650 lines |
| JavaScript under `site/js` | about 8,400 lines | about 5,500 lines |
| Tests | about 9,100 lines | about 6,000 lines, plus the snapshots |
| What a visitor sees | | the same |

## Impact
- Specs: `explore-page` (a figure is an entry over a kind),
  `week-selection` (one URL format), `site-repository` (snapshot tests,
  the comment rule, then the squash).
- Code: `js/charts/` new, the figure modules rewritten as entries,
  `figure_sections.js` and `charts.js` reduced, `sessions_filter.js`
  and `sessions_table_state.js` reduced; `tests/snapshots/` new; the
  markup tests removed.
- Data: none.
